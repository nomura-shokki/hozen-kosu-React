> **用語: ソースコード（source code）とは？**

## 1. このアプリは何をするものか（工数管理とは）

### 1.1 「工数（こうすう）」とは何か

> **用語: 工数（こうすう）とは？**
> 「ある作業に、どれだけの **人の時間** を使ったか」を表す数のこと。たとえば「1人が1時間かけた作業」を基準に、「この作業には3人時（にんじ）かかった」のように数えます。工場や保全（ほぜん：設備の点検・修理）の現場では、「どの作業にどれだけ人手をかけたか」を記録して、ムダを見つけたり、人員計画を立てたりするのに使います。

このアプリは、ひとことで言えば **「従業員が、その日どの作業に何時間使ったかを記録し、集計するシステム」** です。プロジェクトの説明書（`CLAUDE.md`）にもこう書かれています。

> This is a work hours (kosu) management system for tracking employee work time and task categories.
> （これは、従業員の労働時間と作業区分を記録するための、工数管理システムです。）

### 1.2 このアプリでできること（画面の種類）

後ほど §10 で実コードを見ますが、このアプリには次のような画面（ページ）があります。先に全体像をつかんでおきましょう。

| 機能グループ | 何をするか | 該当フォルダ |
|------------|-----------|------------|
| **ログイン / メニュー** | 従業員番号で入り、各機能へ案内する | `MainPage/` |
| **工数入力（Kosu）** | その日の作業内容・時間を記録、一覧・集計・カレンダー表示 | `KosuPage/` |
| **人員（Member）** | 従業員（社員）の登録・一覧・編集・削除 | `MemberPage/` |
| **班員（Team）** | チーム（班）の構成と、班員の工数入力状況の確認 | `TeamPage/` |
| **工数区分定義（Definition）** | 「どんな作業区分があるか」の定義を管理 | `DefinitionPage/` |
| **問い合わせ（Inquiry）** | 要望・不具合・問い合わせの送受信 | `InquirPage/` |
| **管理者（Administrator）** | 全体設定・全工数管理・操作履歴の確認 | `AdministratorPage/` |

> **なぜ「区分定義」が独立しているの？**
> 「作業の種類」は会社や現場によって違い、また時期によって変わります。それを **コードに直接書き込んでしまうと、変更のたびにプログラムを書き換える** ことになり大変です。そこで「作業区分の一覧」を **データとして管理** できるようにしてあります（`kosu_division` モデル。§8で登場）。これは「設定を、プログラムから切り離す」という、よい設計の典型例です。

### 1.3 このアプリを誰が使うか

- **一般の従業員** … 自分の工数を入力する（権限なし）
- **組長・班長クラス** … 自分に加え、班員の入力状況を確認する（`authority`＝権限あり）
- **管理者** … 全体の設定変更、全工数の管理、履歴確認ができる（`administrator`＝管理者フラグあり）

この「3段階の権限」は、後で `member`（人員）モデルの `authority`（権限）と `administrator`（管理者）という2つの真偽値で表現されているのを見ます（§8）。サーバー側の処理（`main_views.py`）でも、`if not member_data.authority:` のように権限チェックが随所に入っています（§7で実例）。

## 2. Webアプリの3者：ブラウザ・サーバー・データベース

Webアプリを理解する最大のコツは、**「登場人物は3人いる」** と知ることです。この3人がメッセージをやり取りして、画面が動きます。

```
┌─────────────┐     ①リクエスト      ┌─────────────┐    ③問い合わせ    ┌─────────────┐
│             │ ──────────────────> │             │ ───────────────> │             │
│  ブラウザ     │                     │  サーバー     │                   │ データベース  │
│ (あなたのPC)  │ <────────────────── │  (Django)    │ <─────────────── │(PostgreSQL) │
│             │     ②レスポンス      │             │    ④結果のデータ   │             │
└─────────────┘                     └─────────────┘                   └─────────────┘
   画面を表示                         処理・判断する                      データを保存・取り出す
```

### 2.1 3者の役割を「レストラン」でたとえる

| 登場人物 | Webでの役割 | レストランでたとえると | 本アプリでの実体 |
|---------|-----------|--------------------|----------------|
| **ブラウザ** | 画面を表示し、ユーザーの操作を受け取る | お客さん（席に座って注文する） | Chrome / Edge などで開いた `Login.tsx` の画面 |
| **サーバー** | 注文を受けて処理し、結果を返す | 厨房（注文を受けて料理を作る） | Django（`main_views.py` などのPythonコード） |
| **データベース** | データを安全に保管・検索する | 食材を保管する冷蔵庫・倉庫 | PostgreSQL（`models.py` で設計した表） |

### 2.2 やり取りの流れ（4ステップ）

1. **リクエスト（request：要求）** … ブラウザがサーバーに「ログインしたい。従業員番号は12345だ」とお願いします。
2. **サーバーの処理** … サーバーが「その番号は登録されているか？」とデータベースに問い合わせます。
3. **データベースの応答** … データベースが「ある／ない」を返します。
4. **レスポンス（response：応答）** … サーバーが「成功」または「エラー」をブラウザに返し、ブラウザが画面を切り替えます。

> **用語: リクエストとレスポンスとは？**
> - **リクエスト** … ブラウザ → サーバー へ送る「お願い」。「この情報をくれ」「このデータを保存してくれ」など。
> - **レスポンス** … サーバー → ブラウザ へ返す「返事」。お願いの結果（成功・失敗・データ本体）が入っています。
> この「お願い→返事」が、Webアプリの **すべての通信の基本単位** です。本アプリでも、画面を開くたび・ボタンを押すたびに、このやり取りが何度も発生しています。

> **用語: HTTP（エイチティーティーピー）とは？**
> ブラウザとサーバーが会話するときの「言葉のルール（プロトコル：約束事）」。HyperText Transfer Protocol の略。`http://localhost:8000` の `http` がこれです。リクエストには「**メソッド**」という種類があり、本アプリでは主に次の4つを使います。

> **用語: HTTPメソッド（GET / POST / PUT / DELETE）とは？**
> リクエストの「目的」を表すラベルです。レストランの注文票の種類だと思ってください。
> - **GET（ゲット）** … 「データをください」（一覧を見る、画面を開く）。例：メニュー画面を表示。
> - **POST（ポスト）** … 「新しいデータを送ります」（登録、ログイン）。例：ログイン情報を送る。
> - **PUT（プット）** … 「既存のデータを書き換えます」（更新）。例：工数の修正。
> - **DELETE（デリート）** … 「このデータを消してください」（削除）。例：工数の削除。
> §7で見る `main_views.py` には、`def post(self, request):`（POSTのとき）、`def get(self, request):`（GETのとき）のように、**メソッドごとに処理が分かれて** 書かれています。

### 2.3 「localhost」と「ポート番号」

開発中、あなたのPCの中でブラウザもサーバーも動かします。そのとき出てくる住所が `localhost`（ローカルホスト：このPC自身）です。

- フロントエンド（React開発サーバー）… `http://localhost:3000`
- バックエンド（Django）… `http://localhost:8000`

> **用語: ポート番号とは？**
> `:3000` や `:8000` の数字。1台のPCの中で、複数のプログラムが同時に通信できるように付ける「部屋番号」のようなもの。同じPC（localhost）でも、3000番の部屋にはReact、8000番の部屋にはDjangoが住んでいる、というイメージです。なぜ番号で分けるかは、後で `settings.py` の `CORS`（コルス）設定（§12）で関係してきます。

## 3. フロントエンドとバックエンドの分離

### 3.1 なぜ画面と処理を別々に作るのか

昔ながらのWebアプリは、サーバーが「完成したHTMLページ」を毎回まるごと作ってブラウザに送っていました。本アプリは違い、**フロントエンド（React）とバックエンド（Django）をきっぱり分けて** います。

```
【昔の方式】
ブラウザ ──「ページちょうだい」──> サーバー ──> HTMLを丸ごと組み立てて返す
（ボタンを押すたびに、画面が真っ白になって、全部読み込み直し）

【本アプリの方式（フロント・バック分離）】
ブラウザ(React) ──「データだけちょうだい（JSON）」──> サーバー(Django)
              <──「はい、データです（JSON）」────────
（Reactが受け取ったデータで、画面の必要な部分だけを書き換える。画面は真っ白にならない）
```

> **用語: JSON（ジェイソン）とは？**
> JavaScript Object Notation の略。データを「名前: 値」のペアの集まりで表す、文字列の書き方。人間にも読みやすく、機械も解釈しやすいので、フロントとバックの間でデータをやり取りする「共通語」として使われます。たとえばログイン成功時、サーバーは次のようなJSONを返します（§7で実物を見ます）。
> ```json
> {"status": "success"}
> ```
> 「status（状態）という名前の値が success（成功）だ」という意味です。

### 3.2 分離のメリット（後任者にとっての利点）

| メリット | 説明 |
|---------|------|
| **担当を分けやすい** | 「画面の見た目」は `frontend/` だけ、「処理・データ」は `kosu/` だけ、と探す場所がはっきりする |
| **画面がサクサク** | データだけ受け取り、必要な部分だけ書き換えるので、画面全体の再読み込みがない |
| **役割が明快** | 「これは見た目の問題（フロント）か、データの問題（バック）か」で原因を切り分けやすい |
| **再利用しやすい** | 同じバックエンドAPIを、別の画面やアプリからも呼べる |

> **保守のヒント:** バグが出たとき、まず「これは画面（フロント）の問題か、処理（バック）の問題か」を切り分けると、調査がぐっと速くなります。**画面の見た目・文言・配置 → `frontend/src/`**、**データの中身・計算・保存 → `kosu/`** が出発点です。

### 3.3 「API」という言葉

> **用語: API（エーピーアイ）とは？**
> Application Programming Interface の略。難しそうですが、ここでは **「フロントとバックがデータをやり取りするための窓口（URL）」** くらいに考えてください。本アプリでは、`/api/login/` `/api/main_menu/` のように、`/api/` で始まるURLが「バックエンドへの注文窓口」です。フロントは、この窓口にリクエストを送り、JSONで返事を受け取ります。

つまり本アプリの構図は、こうです。

```
React（frontend/） ──/api/○○/へリクエスト──> Django（kosu/） ──> PostgreSQL
（見た目・操作）         （JSONでやり取り）        （処理・判断）      （保存）
```

この「`/api/` が窓口」という事実は、後で `hozen_another/urls.py`（§9）に実コードで書かれているのを確認します。

## 4. 全体像：1回のログインで何が起きるか（鳥瞰図）

ここからが本章の核心です。**「ログインボタンを押す」という、たった1つの操作** を題材に、複数のファイルをまたいで処理を追いかけます。まず全体の流れを地図で見て、その後 §5〜§8 で各ファイルを1行ずつ読みます。

> **▼ このあと追いかける処理の流れ（先に日本語で）:**
> ① ユーザーが従業員番号を入力し「ログイン」ボタンを押す（`Login.tsx`）
> → ② Reactが `/api/login/` へ、番号を入れたPOSTリクエストを送る（`Login.tsx`）
> → ③ Djangoが「`/api/login/` は誰が担当？」とURL表を引く（`hozen_another/urls.py` → `kosu/urls.py`）
> → ④ 担当の `Login` クラスの `post` 処理が動く（`main_views.py`）
> → ⑤ 「その番号は人員データにあるか？」をデータベースに問い合わせる（`models.py` の `member` 表）
> → ⑥ あれば「成功」、なければ「エラー」のJSONを返す（`main_views.py`）
> → ⑦ Reactが返事を見て、成功ならメインメニューへ画面遷移、失敗ならエラー表示（`Login.tsx` → `index.tsx`）

```
[ブラウザ] Login.tsx
   │  ① 従業員番号 12345 を入力 → ログインボタン押下
   │  ② api.post("/api/login/", { employee_no: 12345 })
   ▼
[サーバー] Django
   │  ③ hozen_another/urls.py が「/api/ → kosu.urls」、kosu/urls.py が「login/ → Login」と振り分け
   │  ④ main_views.py の Login.post() が実行される
   │  ⑤ member.objects.filter(employee_no=12345).exists() で
   ▼     データベースに「この番号いる？」と問い合わせ
[DB] PostgreSQL（models.py で設計した member 表）
   │  ⑥ 「いる」or「いない」を返す
   ▼
[サーバー] Django
   │  ⑦ いれば {"status":"success"} / いなければ {"status":"error", ...}
   ▼
[ブラウザ] Login.tsx
      ⑧ success なら navigate("/")（メインメニューへ）/ error ならエラー表示
      ⑨ index.tsx のルート定義が「/」→ MainMenu を表示
```

この1本の処理を完全に理解できれば、本アプリの **他のすべての機能も同じパターン** で動いていることが分かります。工数入力も、人員登録も、削除も、「フロントがリクエスト → urlsが振り分け → viewsが処理 → modelsの表を読み書き → JSONで返す」という同じ骨格です。**この章で1本通せば、残りは応用です。**

## 5. 実コード①：Login.tsx（フロントの入口）を1行ずつ

それでは実物のコードを読みます。最初は、ユーザーが最初に触れる画面 `frontend/src/MainPage/Login.tsx`（全71行）です。

> この章では **処理（JavaScript/TypeScript）の流れ** に注目します。画面の見た目（JSXとCSS）の詳しい解説は `03_Web基礎_HTML_CSS.md` にあります。ここでは「ログインの処理が、どこからどこへつながっているか」を中心に読みます。

### 5.1 ファイル冒頭：import（道具の取り寄せ）― 1〜6行目

> **▼ このコードがやること（先に日本語で）:** このファイルが使う「道具（部品やライブラリ）」を、他のファイルから取り寄せます。料理でいう「材料と調理器具を、棚から作業台に出す」工程です。

### 5.3 ログイン処理の本体：handleSubmit ― 13〜31行目

ここがこの画面の心臓部です。ボタンを押したときに実行される処理を、丁寧に読みます。

> **▼ このコードがやること（先に日本語で）:** 「ログイン」ボタンが押されたら、(1) 画面の標準動作を止め、(2) 古いエラー表示を消し、(3) 入力された番号をサーバーの `/api/login/` へ送り、(4) 返事が「成功」ならメインメニューへ移動、(5) 失敗ならエラーメッセージを表示する ―― という一連の流れを行います。

```tsx
  // ① 送信時に呼ばれる関数(asyncは「待つ処理」を含む印)
  const handleSubmit = async (event: React.FormEvent) => {
    // ② ブラウザ標準の「ページ再読み込み」を止める
    event.preventDefault();
    // ③ 前回のエラー表示を消す(空文字にする)
    setErrorMessage("");

    // ④ ここから「失敗するかもしれない処理」
    try {
      // ⑤ サーバーへ番号を送る
      const response = await api.post("/api/login/", { employee_no: Number(employee_no) });
      // ⑥ サーバーからの返事の中身(JSON)を取り出す
      const data = response.data;
      // ⑦ 返事が「成功」だったら
      if (data.status === "success") {
        // ⑧ メインメニュー("/")へ画面移動
        navigate("/");
      // ⑨ 「成功」以外だったら
      } else {
        // ⑩ サーバーのメッセージを表示
        setErrorMessage(data.message || "サーバーエラーが発生しました。");
      }
    // ⑪ 通信そのものが失敗したとき(例外発生)
    } catch (err) {
      // ⑫ それが通信由来のエラーなら
      if (axios.isAxiosError(err)) {
        // ⑬ 401(未認証)なら、ログイン画面へ戻す
        if (err.response?.status === 401) navigate("/login");
        // ⑭ それ以外は、サーバーのメッセージを表示
        else setErrorMessage(err.response?.data.message);
      // ⑮ 通信以外の謎のエラー
      } else setErrorMessage("不明なエラーが発生しました。IT担当者に連絡してください。");
    }
  };
```

1行ずつ意味を確認します。

- **①** `const handleSubmit = async (event) => { ... }` … 「ログインボタンが押されたとき（フォーム送信時）に呼ばれる関数」を定義。`event`（イベント）には「何が起きたか」の情報が入っています。
  > **用語: async / await（エイシンク / アウェイト）とは？**
  > サーバーとの通信は「お願いしてから返事が来るまで、少し時間がかかる」処理です。`await`（アウェイト：待つ）は「この処理の返事が来るまで、ここで待ってから次へ進む」という命令。`await` を使う関数には、頭に `async`（非同期：あとで返ってくる）を付ける決まりです。「料理を注文して、出来上がるのを待ってから食べる」イメージ。
- **②** `event.preventDefault()` … フォームは標準では「送信するとページが再読み込みされる」動作をします。Reactでは自分で処理したいので、この標準動作を **止めます**。これを忘れると画面が一瞬リロードされてしまいます。
- **③** `setErrorMessage("")` … 前回の失敗で出ていたエラー表示を、いったん消します（§5.2の `errorMessage` state を空にする）。
- **④** `try {` … 「この中の処理は失敗するかもしれない。失敗したら `catch`（⑪）へ飛ぶ」という構文。
  > **用語: try / catch（トライ / キャッチ）とは？**
  > 「失敗するかもしれない処理」を `try { }` で囲み、もし失敗（例外）が起きたら `catch { }` の中で受け止める仕組み。通信は「サーバーが落ちている」「ネットが切れた」など失敗しうるので、必ずこれで守ります。綱渡りの下に張る「安全ネット」のイメージ。
- **⑤** `const response = await api.post("/api/login/", { employee_no: Number(employee_no) });` … **ここが通信の本体** です。
  - `api.post(...)` … POSTメソッド（新規送信。§2.2）で、`/api/login/` という窓口へリクエストを送る。
  - `{ employee_no: Number(employee_no) }` … 送るデータ。`Number(...)` で **文字列を数値に変換** しています。
  > **なぜ `Number(...)` で変換するの？** `<input type="number">` の入力値は、JavaScript側では実は **文字列**（例: `"12345"`）として届きます。サーバー側は数値の従業員番号を期待しているため、`Number("12345")` → `12345` と数値化してから送っています。
  - `await` が付いているので、サーバーの返事が来るまでここで待ち、返事を `response` に入れます。
- **⑥** `const data = response.data;` … 返事の中から「中身（JSONデータ）」を取り出して `data` へ。
- **⑦** `if (data.status === "success")` … 中身の `status` が `"success"` か判定。`===` は「完全に等しいか」の比較（型まで一致を確認する厳密比較）。
- **⑧** `navigate("/")` … 成功なら、`"/"`（メインメニュー）へ画面を移動。`useNavigate`（§5.2④）で用意した道具を使っています。
- **⑨⑩** 成功以外なら、サーバーが返したメッセージ（`data.message`）を画面に表示。`||`（オア）は「左がなければ右を使う」。メッセージが無いときは「サーバーエラーが発生しました。」を出します。
- **⑪** `catch (err)` … 通信そのものが失敗したとき（サーバーがエラーを返した、ネットが切れた等）にここへ来ます。
- **⑫** `axios.isAxiosError(err)` … そのエラーが「通信由来のものか」を判定。
- **⑬** `if (err.response?.status === 401) navigate("/login")` … サーバーが **401** を返したら、ログイン画面へ戻します。
  > **用語: ステータスコード（status code）とは？**
  > サーバーが「処理の結果がどうだったか」を3桁の番号で表す共通ルール。代表的なもの：
  > - **200** … 成功（OK）
  > - **400** … リクエストが不正（Bad Request。入力ミスなど）
  > - **401** … 未認証（Unauthorized。ログインが必要）
  > - **403** … 権限なし（Forbidden。ログインはしているが、この操作は許されない）
  > - **404** … 見つからない（Not Found）
  > - **500** … サーバー内部エラー
  > 本アプリでは「401ならログイン画面へ飛ばす」という方針があり、サーバー側（§7）でも未ログイン時に401を返しています。フロントとバックで **401＝再ログイン** という約束が一致しているわけです。
  > `?.`（オプショナルチェーン）は「`err.response` が存在すれば `.status` を見る、無ければ何もしない（エラーにしない）」という安全な書き方です。
- **⑭⑮** それ以外のエラーは、サーバーのメッセージ、または「不明なエラー」を表示します。

> **この17行が、本アプリの「通信処理の型」です。** 工数入力も人員登録も、「`try` で囲んで `api.post`/`api.get` し、`status` を見て分岐、`catch` でエラー処理」という **同じパターン** を繰り返します。ここを理解すれば、他の画面の処理も読めます。

  > **用語: views（ビュー）とは？**
  > Djangoで「リクエストを受け取って、処理して、レスポンスを返す」役割の場所。本アプリでは機能ごとにファイルを分けています（`main_views.py`＝ログイン等、`kosu_views.py`＝工数入力、…）。「厨房の中で、料理ジャンルごとに担当を分けている」イメージ。

### 6.2 URL対応表の本体：urlpatterns ― 14〜103行目

`urlpatterns`（ユーアールエル・パターンズ）という名前のリスト（一覧）に、URLと処理の対応を1行ずつ並べます。代表的な行を読みましょう。

> **▼ このコードがやること（先に日本語で）:** 「このURLが来たら、この処理クラスを呼ぶ」という対応を、機能の数だけ並べた一覧です。

```python

  # ⑤ /help_pass/ → HelpPass が担当
  path('help_pass/', main_views.HelpPass.as_view(), name='help_pass'),

  path('main_menu/', main_views.Menu.as_view(), name='main_menu'),
  # ⑦ 工数メニュー

  # ⑨ ID付きURL(後述)
  path('kosu_update/<int:pk>/', kosu_views.KosuUpdate.as_view(), name='kosu_update'),
```

`path` の中身は3つの部分でできています。`path('login/', main_views.Login.as_view(), name='login')` を分解すると：

1. **`'login/'`** … URLの文字列（パターン）。`/api/login/` の `api/` を除いた部分。
2. **`main_views.Login.as_view()`** … このURLが来たときに呼ぶ処理。「`main_views` ファイルの中の `Login` クラス」を担当に指定。`.as_view()` は「クラスを、URLから呼べる形に変換する」おまじない。
3. **`name='login'`** … この対応に付ける「あだ名」。コードの他の場所からURLを参照するのに使えます。

> **ここで `Login.tsx` とつながります！**

### 7.2 ログイン処理：Login クラス ― 78〜102行目

いよいよ核心です。`Login.tsx` がPOSTしたリクエストを、この `Login` クラスの `post` メソッドが受け取ります。

> **▼ このコードがやること（先に日本語で）:** フロントから送られてきた従業員番号を取り出し、(1) JSONとしてきちんと読めるか確認し、(2) その番号が人員データ（`member`表）に登録されているか調べ、(3) 登録があれば「ログイン状態」を覚え（セッション保存）、使用する工数区分定義の最新版も覚えて「成功」を返し、(4) 登録がなければ「エラー」を返します。

```python
# ログイン
# ① ログイン処理(APIView を土台に)
class Login(APIView):
  # POST処理
  # ② POSTリクエストが来たときの処理
  def post(self, request):
    # ③ 失敗しうる処理の開始
    try:
      # 送られてきたデータ確認
      # ④ リクエスト本文をJSONとして読み込む
      data = json.loads(request.body)
      # ⑤ その中から従業員番号を取り出す
      input_number = data.get('employee_no')
    # ⑥ JSONとして読めなかったら
    except json.JSONDecodeError:
      # ⑦ 400エラーを返す
      return JsonResponse({'status': 'error', 'message': 'JSON形式が正しくありません。'}, status=status.HTTP_400_BAD_REQUEST)

    # POSTされた従番が人員データにある場合、セッションに保存&最新工数区分定義取得
    # ⑧ その番号が member 表にあるか?
    if member.objects.filter(employee_no=input_number).exists():
      # ⑨ あれば「ログイン中の番号」を覚える(セッション)
      request.session['login_No'] = input_number
      # ⑩ 工数区分定義の最新版を取得
      def_Ver = kosu_division.objects.order_by("id").last()

      # 取得した工数区分定義をセッションに保存
      # ⑪ もし定義が1件も無ければ
      if not def_Ver:
        # ⑫ エラー
        return JsonResponse({'status': 'error', 'message': '利用可能な工数区分がありません。ERROR052'}, status=status.HTTP_400_BAD_REQUEST)
      # ⑬ 定義があれば
      else:
        # ⑭ その定義名を覚える(セッション)
        request.session['input_def'] = def_Ver.kosu_name
        # ⑮ 「成功」を返す ← Login.tsx の⑦へ!
        return JsonResponse({'status': 'success'})

    # ⑯ 番号が member 表に無ければ
    else:
      # ⑰ エラー
      return JsonResponse({'status': 'error', 'message': '入力された従業員番号は登録がありません。ERROR048'}, status=status.HTTP_400_BAD_REQUEST)
```

1行ずつ読みます。

- **①** `class Login(APIView):` … 「`Login` というAPIのビューを作る」。括弧の中の `APIView` は「これを土台にする（継承する）」という意味。
  > **用語: クラス（class）と継承（けいしょう）とは？**
  > **クラス** は「ある種類の処理・データをひとまとめにした設計図」。**継承** は「既存のクラスの機能を引き継いで、自分のクラスを作る」こと。`Login(APIView)` は「`APIView` が持つ便利機能（リクエストの受け取り方など）を引き継いだ上で、ログイン専用の処理を足す」という意味です。料理の「基本のレシピを土台に、自分流のアレンジを足す」イメージ。
- **②** `def post(self, request):` … 「POSTリクエストが来たら、この処理を実行」。`request`（リクエスト）に、フロントから送られた情報すべてが入っています。`def` は「関数（処理のまとまり）を定義する」Pythonの命令です。
  > **なぜ `post` という名前？** §2.2のHTTPメソッドと対応しています。`Login.tsx` が `api.post(...)`（POST）で送ったので、サーバー側も `def post` が反応します。もしGETで来たら `def get` が呼ばれます。**メソッド名が、HTTPメソッドと一致** しているのがDRF（後述）のお約束です。
- **③〜⑦** `try / except` … `json.loads(request.body)` でリクエスト本文をJSONとして読み込みます。`data.get('employee_no')` で、その中から従業員番号を取り出します。もし送られた中身がJSONとして壊れていたら（`JSONDecodeError`）、400エラー（不正なリクエスト）を返します。
  > **⑤ の `.get('employee_no')` に注目:** これは `Login.tsx`（§5.3⑤）が `{ employee_no: Number(employee_no) }` という名前で送ったデータと **キー名が一致** しています。フロントが `employee_no` という名前で送り、バックが `employee_no` という名前で受け取る ―― この **名前の一致** が、フロントとバックの「契約」です。どちらかが名前を変えると通信が壊れます。
- **⑧** `if member.objects.filter(employee_no=input_number).exists():` … **データベースへの問い合わせ** です。ここが §4 の鳥瞰図で「⑤データベースに問い合わせ」と書いた部分。
  - `member.objects` … `member` 表（人員表。§8で設計を見ます）の全データ。
  - `.filter(employee_no=input_number)` … 「従業員番号が、入力された番号と一致する行だけ」に絞り込み。
  - `.exists()` … 「そういう行が1つでもあるか？（True / False）」を返す。
  > つまりこの1行は「**入力された従業員番号は、人員表に登録されているか？**」をデータベースに尋ねています。これがログイン認証の本体です。本アプリのログインはパスワードではなく「番号が登録されているか」で判定する方式です。
- **⑨** `request.session['login_No'] = input_number` … 登録があれば、**セッション** に「ログイン中の従業員番号」を記録します。
  > **用語: セッション（session）とは？**
  > 「この人はログイン済みだ」という状態を、サーバー側が一定期間覚えておく仕組み。ログインのたびにブラウザに小さな合言葉（クッキー）を渡し、次回以降のリクエストでその合言葉を見て「あ、さっきログインした人だ」と分かるようにします。これにより、画面を移動しても **毎回番号を入れ直さずに済む** のです。§7.4で、他のメニュー画面がこのセッションを使って「ログイン済みか」を確認しているのを見ます。
- **⑩** `def_Ver = kosu_division.objects.order_by("id").last()` … 工数区分定義（作業区分の一覧。§8の `kosu_division`）の中から、**ID順で最後＝最新版** を取り出します。`.order_by("id")` で番号順に並べ、`.last()` で最後の1件を取得。
- **⑪⑫** もし定義が1件も無ければ（`not def_Ver`）、`ERROR052` という番号付きエラーを返します。
  > **なぜエラーに番号（ERROR052）を付けるの？** ユーザーが「エラーが出た」と言ってきたとき、番号があれば「どこで起きたエラーか」をコードから即座に特定できます。保守をラクにする工夫です。
- **⑭** `request.session['input_def'] = def_Ver.kosu_name` … 最新定義の名前もセッションに記録。以後の工数入力で「どの定義を使うか」の基準になります。
- **⑮** `return JsonResponse({'status': 'success'})` … **すべてOKなら「成功」を返します。** この `{'status': 'success'}` というJSONが、ネットワークを通って `Login.tsx`（§5.3⑥⑦）の `data.status === "success"` で受け取られ、`navigate("/")` でメインメニューへ進みます。**ここで処理が1周してフロントへ戻る** のです。
- **⑯⑰** 番号が登録されていなければ、`ERROR048`「入力された従業員番号は登録がありません」を400エラーで返します。これは `Login.tsx`（§5.3⑭）の `catch` 側で受け取られ、エラーメッセージとして画面に表示されます。

> **これで §4 の鳥瞰図が完成しました。**
> `Login.tsx`（番号入力・送信）→ `urls.py`（`/login/` を `Login` へ振り分け）→ `main_views.py`（`member` 表に問い合わせ・成功/失敗を判定）→ JSONで返事 → `Login.tsx`（成功なら画面遷移）。**1本の処理が、複数のファイルをまたいで完結する** ―― この骨格が、本アプリのすべての機能に共通します。

### 7.4 認証チェックの共通パターン ― Menu クラス 204〜237行目

`main_views.py` の各メニュー画面（`Menu`・`MemberMenu` など）には、**ほぼ同じ「認証チェック」のパターン** が繰り返し現れます。`Menu`（メインメニュー）を例に見ます。

```python
class Menu(APIView):

    login_no = request.session.get('login_No')

    def_ver = request.session.get('input_def')

    # ⑥ 定義名も無ければ
    if not def_ver:
      return Response({'status': 'error', 'message': '使用する工数区分定義情報が確認できません。'}, status=status.HTTP_401_UNAUTHORIZED)

    try:
      # ⑦ その番号の人員データを取得
      member_data = member.objects.get(employee_no=login_no)
    # ⑧ もし見つからなければ
    except member.DoesNotExist:
      return Response({'status': 'error', 'message': 'ユーザー情報が見つかりません。'}, status=status.HTTP_401_UNAUTHORIZED)
    # ... 設定データ取得、シリアライザでJSON化して返す ...
```

ここで `Login.tsx`（§5.3⑬）の「401ならログイン画面へ」が効いてきます。`Menu` 画面を開いたとき、**もしログインしていなければ ⑤ で401を返し**、フロントはそれを見て自動的にログイン画面へ戻します。**「未ログインの人を、ログイン画面へ追い返す」仕組みが、フロント（401を見て遷移）とバック（401を返す）の協力で実現** されているのです。

> **保守のヒント:** `main_views.py` の各メニュークラスは、この「セッション確認 → 無ければ401 → あれば人員データ取得 → 権限チェック → データをJSONで返す」という **判で押したような構造** をしています。1つ理解すれば、残りはほぼ同じパターンの繰り返しです。`MemberMenu`（258行付近）では、加えて `if not member_data.authority:`（権限が無ければ403）という **権限チェック** が入っているのが違いです。

## 8. 実コード④：models.py（データの設計図）を1行ずつ

§7で `member.objects.filter(...)` のように、データベースの表に問い合わせていました。その **表の設計図** が `kosu/models.py` です。「どんなデータを、どんな形で保存するか」を定義しています。

> **用語: データベース / テーブル / レコード / カラム とは？**（表計算ソフトでたとえる）
> - **データベース（database：DB）** … データを保管する「倉庫」全体。Excelブック1冊のイメージ。
> - **テーブル（table：表）** … 倉庫の中の1つの「表（シート）」。本アプリの `member`（人員）・`Business_Time_graph`（工数）などが、それぞれ1枚の表。
> - **レコード（record：行）** … 表の1行。「従業員1人ぶんの情報」「工数記録1件」など。

1行ずつ、カラム定義の読み方を学びます。

- **③** `employee_no = models.IntegerField('従業員番号')` … 「`employee_no` という名前の、整数（Integer）型の列。表示名は『従業員番号』」。**これが §7.2⑧ の `filter(employee_no=...)` で照合された鍵** です。
  > **用語: フィールド型（Field）とは？**
  > カラムの「データの種類」を指定するもの。`IntegerField`＝整数、`CharField`＝短い文字列、`TextField`＝長い文字列、`BooleanField`＝True/False、`DateField`＝日付、`DateTimeField`＝日時。型を決めることで、データベースが「この列には数字しか入らない」などと管理してくれます。
- **④** `name = models.CharField('氏名', max_length=100)` … 文字列の列。`max_length=100` は「最大100文字」。`CharField` は必ず最大長を指定します。
- **⑤** `shop = models.CharField('ショップ', choices=shop_list, max_length=15)` … `choices=shop_list`（②の一覧）を指定すると、**決められた選択肢からしか選べない列** になります。画面ではドロップダウンになります。
- **⑥⑦** `authority`・`administrator` … `BooleanField`（真偽値＝True/False）。§1.3で説明した「3段階の権限」を、この2つの旗（フラグ）で表現しています。§7.4で `if not member_data.authority:` のように使われていました。
- **⑧⑨** `break_time1` 〜 … 勤務形態（1直・2直・3直・常昼・連1直・連2直の6種）ごとに、昼休憩＋残業休憩3つ、計24個の休憩時間カラムが並びます。`max_length=9` で、`#11401240` のような独自形式（`#` ＋ 開始時刻4桁 ＋ 終了時刻4桁）で休憩時間を表します。
  > **なぜ休憩時間がこんなに多いの？** 工場では勤務シフト（直）ごとに休憩時刻が違うためです。工数を正しく計算するには「いつ休憩で、いつ働いていたか」が必要なので、人ごと・勤務形態ごとに休憩時刻を持たせています。
- **⑩** `def __str__(self): return self.name` … この行（レコード）を文字で表すときの見た目。Django管理画面などで「ID番号」ではなく「氏名」で表示され、人間に分かりやすくなります。

> **用語: null=True / blank=True とは？**
> モデル定義でよく見る指定。`null=True` は「データベース上で空（未設定）を許す」、`blank=True` は「入力フォーム上で空欄を許す」。`pop_up1 = models.CharField(..., null=True, blank=True)` のように、必須でない項目に付けます。

> **`pk`（背番号）はどこ？** member モデルには `id` の定義が見当たりませんが、Djangoは **自動で `id` という主キー（§6.2の pk）を各モデルに付けます**。これが §6.2 の `/kosu_update/<int:pk>/` で使われる背番号です。`settings.py`（§12）の `DEFAULT_AUTO_FIELD` がこの自動IDの型を決めています。

`AsyncTask` と `History` には `save()` メソッドが上書きされており、「レコードが上限（`MAX_RECORDS`）を超えたら、古いものから自動削除する」仕組みが入っています。これにより、ログが無限に溜まってデータベースが膨張するのを防いでいます。

```python
class AsyncTask(models.Model):
  # 保持する最大件数
  MAX_RECORDS = 1000

  # タスクの一意なID
  task_id = models.CharField(max_length=255, unique=True)
  # 状態(pending/success/error)
  status = models.CharField(max_length=50, choices=[
    ('pending', 'Pending'),
    ('success', 'Success'),
    ('error', 'Error')
  ])
  # 結果
  result = models.TextField(null=True, blank=True)
  # 作成日時(自動)
  created_at = models.DateTimeField(auto_now_add=True)
  # 更新日時(自動)
  updated_at = models.DateTimeField(auto_now=True)

  # 保存時に上限を超えたら古い順に削除
  def save(self, *args, **kwargs):
    super().save(*args, **kwargs)
    current_count = self.__class__.objects.count()
    if current_count > self.MAX_RECORDS:
      excess_count = current_count - self.MAX_RECORDS
      oldest_records = self.__class__.objects.order_by('created_at')[:excess_count]
      for record in oldest_records:
        record.delete()
```

> **`models.py` のまとめ:** ここは **データベースの設計図** です。`member`（人員）でログイン認証し、`Business_Time_graph`（工数）に記録を貯め、`kosu_division`（定義）で作業区分を管理します。**「このデータ項目はどこに保存されている？」と思ったら、まずこの `models.py` で該当モデルのカラムを探す** のが調査の起点になります。

## 9. 実コード⑤：hozen_another/urls.py（最上位のルーター）を1行ずつ

§6で見た `kosu/urls.py` は「`/api/login/` のうち `login/` の部分」を担当していました。では「`/api/` という入口」自体は、どこで決まっているのでしょうか。それが、プロジェクト全体の **最上位のURL対応表** `hozen_another/urls.py`（全18行）です。

> **用語: プロジェクト と アプリ の違い（Django）**
> Djangoでは、**プロジェクト（project）** が「サイト全体」、**アプリ（app）** が「その中の機能のまとまり」です。本アプリでは `hozen_another/` がプロジェクト（設定・最上位URL）、`kosu/` がアプリ（工数管理の実体）。`hozen_another/urls.py` が「玄関の交通整理」、`kosu/urls.py` が「各部屋の中の案内図」という階層関係です。

> **▼ このコードがやること（先に日本語で）:** ブラウザから来たURLを、その先頭部分で大きく振り分けます。`/admin/` はDjango管理画面へ、`/api/` で始まるものは `kosu` アプリのURL表（§6）へ、それ以外は全部Reactの画面へ、という3つの大きな分岐です。

```python
# ① Django標準の管理画面
from django.contrib import admin
# ② URL定義の道具(include=他のurls.pyを取り込む)
from django.urls import path, include, re_path
# ③ React表示処理とmanifest処理を取り寄せ
from kosu.views.main_views import react_view, manifest
# ④ 設定値を読む
from django.conf import settings
# ⑤ 静的ファイル配信の道具
from django.conf.urls.static import static



# ⑥ 最上位のURL対応表
urlpatterns = [
  # ⑦ /admin/ → Django管理画面
  path('admin/', admin.site.urls),
  # ⑧ /BA で始まるURL → kosu/urls.py へ
  path('BA', include('kosu.urls')),
  # ⑨ /api/ で始まるURL → kosu/urls.py へ ← 重要!
  path('api/', include('kosu.urls')),
  # ⑩ /manifest.json → アプリ情報を返す
  path('manifest.json', manifest),
  # ⑪ admin以外の全URL → Reactの画面を返す
  re_path(r'^(?!admin).*$', react_view),
]

# ⑫ 開発モードのときだけ
if settings.DEBUG:
    # ⑬ 静的ファイル配信を追加
    urlpatterns += static(settings.STATIC_URL, document_root=settings.STATIC_ROOT)
```

1行ずつ読みます。

- **②** `include`（インクルード）… 「別の `urls.py` を、ここに取り込む」道具。これで階層的なURL構成ができます。
- **⑦** `path('admin/', admin.site.urls)` … `/admin/` で始まるURLは、Django標準の **管理画面** へ。これはDjangoが用意してくれる、データベースを直接見たり編集したりできる便利な裏画面です。
- **⑧⑨** `path('api/', include('kosu.urls'))` … **ここが §6 とのつながり** です。`/api/` で始まるURLが来たら、後ろの部分を `kosu/urls.py`（§6）に渡して、そこで担当を決めてもらいます。
  > つまり `/api/login/` は、**まずここ（⑨）で「`api/` だから `kosu.urls` へ」と振り分けられ、次に `kosu/urls.py`（§6.2②）で「`login/` だから `Login` へ」と振り分けられる**、2段階のルーティングを通っていたのです。`/BA` でも同じ `kosu.urls` を使えるようにしてあります（別経路でのアクセス用）。
- **⑩** `path('manifest.json', manifest)` … `/manifest.json` はアプリ情報（アプリ名・アイコン色など）を返す処理へ。スマホでホーム画面に追加したときの表示などに使われます。
- **⑪** `re_path(r'^(?!admin).*$', react_view)` … **これが「分離型アプリ」の肝** です。
  - `re_path` … 正規表現（パターンマッチ）でURLを指定する道具。
  - `r'^(?!admin).*$'` … 「`admin` で **始まらない** あらゆるURL」というパターン。
  - `react_view` … そのURLに対して、Reactのページ（`index.html`）を返す処理。
  > **なぜこれが必要？** 本アプリはフロントとバックが分離しているので、`/`・`/kosu-menu`・`/member-list` など **画面用のURLは、すべてReactに任せます**。ユーザーがどの画面URLを開いても（adminとapi以外なら）、サーバーは同じReactの土台（`index.html`）を返し、**実際にどの画面を出すかはReact側（§10の `index.tsx`）が決める** のです。これを **SPA（エスピーエー：シングルページアプリケーション）** と呼びます。
  > **用語: SPA（Single Page Application）とは？** 「1枚のHTML土台を最初に読み込み、その後は画面の中身だけをJavaScriptで差し替える」方式のWebアプリ。ページ全体を読み込み直さないので、画面遷移が速くスムーズです。本アプリはこの方式です。
- **⑫⑬** `if settings.DEBUG:` … `settings.py` の `DEBUG` が `True`（開発モード）のときだけ、静的ファイル（CSS・画像など）の配信設定を追加します。本番では別の方法（WhiteNoise。§12）で配信するため、ここは開発用です。

> **`hozen_another/urls.py` のまとめ:** これは **玄関の交通整理** です。`/admin/`→管理画面、`/api/`→バックエンド処理（kosu/urls.py 経由）、それ以外→Reactの画面、という3分岐。**フロント（画面URL）とバック（apiURL）の分離が、この1ファイルで実現** されています。

## 10. 実コード⑥：index.tsx（フロントの全ルート）を1行ずつ

§9の⑪で「画面用URLはReactに任せる」と分かりました。では、Reactは「どのURLで、どの画面部品を出すか」を **どこで決めている** のか。それが、フロントエンドの司令塔 `frontend/src/index.tsx`（全180行）です。

> **用語: ルーター（router）とは？**

## 15. 演習問題

手を動かして、この章の地図を体に入れましょう。**まずは「読んで探す」演習** から始め、コードの変更は慎重に（壊しても安全なローカル環境で）行ってください。

1. **処理の追跡（ペンと紙で）**：ログインボタンを押してからメインメニューが出るまで、本章で読んだ6ファイルを **どの順で通るか** を、矢印で書き出してみる（§4・§10の最後のまとめが答え）。

2. **URLの逆引き**：`kosu/urls.py`（§6）を開き、URL `member_new/` の担当が **どのファイルのどのクラス** か答える。さらに、そのクラスがどの `_views.py` にあるか確認する。

3. **モデルのカラム探し**：`kosu/models.py`（§8）で、「従業員が管理者かどうか」を表すカラムの **名前と型** を答える（ヒント：§8.2⑦）。

4. **設定の確認**：`hozen_another/settings.py`（§12）で、(a) 1ページに何件表示するか、(b) どのデータベースを使うか、(c) 言語は何か、を探して答える（§12.4・§12.6）。

7. **（応用・要注意）初期管理者の確認**：`main_views.py` の `Help` クラス（§7.3）を読み、「全データを初期化したら、どの従業員番号でログインできるか」を答える（ヒント：§7.3⑦）。これは引き継ぎで知っておくべき重要事項です。

## 16. この章のまとめ

- **このアプリの目的** は工数（作業にかけた人の時間）の記録・集計。ログイン／工数／人員／班員／定義／問い合わせ／管理者の各機能があり、フォルダがそれに対応する（§1・§13）。
- **Webアプリには3者** がいる ―― **ブラウザ**（画面）・**サーバー**（処理）・**データベース**（保存）。リクエストとレスポンスでやり取りし、HTTPメソッド（GET/POST/PUT/DELETE）で目的を区別する（§2）。
- 本アプリは **フロント（React）とバック（Django）を分離** し、**JSON** でデータをやり取りする。窓口は **`/api/`** で始まるURL（§3・§9）。
- **ログイン1本を6ファイルで端から端まで追った**：`Login.tsx`（入力・送信）→ `hozen_another/urls.py`（`/api/`→kosu）→ `kosu/urls.py`（`login/`→Login）→ `main_views.py`（`member` 表に問い合わせ・成功/失敗判定・セッション保存）→ JSON返却 → `Login.tsx`（`navigate("/")`）→ `index.tsx`（`/`→`MainMenu`表示）。**他の全機能も同じ骨格**（§4〜§10）。
- **`models.py`** はデータの設計図。1モデル＝1テーブル、1フィールド＝1カラム。`member`（人員。`authority`/`administrator` で3段階権限）・`Business_Time_graph`（工数）・`kosu_division`（定義。1レコードに最大50区分）が中核。`id`（pk）は自動付与（§8）。
- **技術スタック** は React / TypeScript / Django / DRF / PostgreSQL を中心とした **定番で保守しやすい組み合わせ**。7基準で見ると「情報が豊富・保守しやすい・将来性が高い」のが強み（§11）。
- **`settings.py`** はアプリの設定ダイヤル盤。秘密情報は **`.env`** から読み（漏洩防止）、`INSTALLED_APPS` で `kosu` を有効化、`CORS` で別ポート通信を許可、`DATABASES` でPostgreSQL接続、`STATICFILES`/`TEMPLATES` でReactのビルド成果物を配信（§12）。
- **フォルダ構成の地図** を持っておけば、「どこを直せばよいか」で迷わない。見た目・処理は `frontend/src/`、データ・計算・権限は `kosu/`、設定は `hozen_another/`（§13）。

これで、このアプリの **全体像という地図** が手に入りました。次は、実際に自分のPCでこのアプリを動かせるようにする環境構築です。

次は、「[01_環境構築.md](./01_環境構築.md)」へ進みます。
