## 0. 前提知識：テストとは何か、なぜ書くのか

### 0.1 テストとは「機械にやらせる動作確認」

> **テスト（test）とは？**
> プログラムが「期待どおりに動くか」を確かめるための、**別のプログラム**。テスト対象の本体コードを呼び出し、「こういう入力を与えたら、こういう結果になるはず」を機械的にチェックします。

たとえば、本アプリのログイン機能には「従業員番号 `12345` を送ったらログイン成功する」という期待があります。これを手で確認するなら、毎回ブラウザを開いて、番号を打って、ボタンを押して、画面を見る……という作業が要ります。テストコードを書いておけば、**コマンド1つでこの確認を一瞬で・何百回でも** やってくれます。

> **▼ たとえ話：健康診断**
> テストは、人間の **健康診断** に似ています。体のあちこち（血圧・血液・視力…）を一通り測り、「基準値の範囲内か」を確認します。プログラムも同じで、機能のあちこちに「測定項目（テスト項目）」を置いておき、コマンドを流すたびに **全項目を一斉に検査** します。どこか1つでも基準を外れたら、テストは「ここが異常です」と赤字で教えてくれます。
>
> 健康診断を毎年受けるように、テストも **コードを直すたびに** 流します。そうすれば「気づかないうちに体（プログラム）の別の場所が悪くなっていた」を早期発見できます。

### 0.2 なぜ手作業ではなくテストコードなのか

| 確認方法 | かかる時間 | 見落とし | 何百回の繰り返し |
|----------|-----------|----------|------------------|
| **手作業**（毎回ブラウザを操作） | 1機能で数分、全機能で数時間 | 起きやすい（人間だから） | 苦痛・現実的でない |
| **テストコード**（コマンド1つ） | 全部で数秒〜数十秒 | 起きにくい（毎回同じ手順） | 何度でも一瞬 |

> **なぜ？ テストが「保守」で最も効く理由**
> あなたは後任者として、これからこのアプリを **直し続けます**。1か所直すと、関係なさそうな別の場所が連鎖的に壊れること（これを **デグレード／リグレッション＝後退バグ** と呼びます）がよくあります。テストがあれば、修正後にコマンドを流すだけで「壊していないか」が即わかります。**テストは「安心して直すための保険」** です。

### 0.3 本アプリのテストは2種類ある

| 種類 | 対象 | 道具 | 場所 | 実行コマンド |
|------|------|------|------|--------------|
| **フロントのテスト** | React の画面・部品 | Vitest ＋ React Testing Library | `frontend/src/tests/` | `npm run test:run` |
| **バックのテスト** | Django のAPI・モデル・関数 | Django `TestCase` ＋ `APIClient` | `kosu/tests/` | `python manage.py test ...` |

この章では、両方を実物のコードで読みます。まずは「どんなテストでも共通の考え方」である **3ステップ** を押さえましょう。

## 1. テストの3ステップ（準備→実行→検証）

ほぼすべてのテストは、次の3つの段階でできています。英語の頭文字をとって **AAA（トリプルA）** とも呼ばれます。

```
1. 準備（Arrange / アレンジ） … テストの前提を整える
                               （データを作る・にせものを用意する・画面を描く）
2. 実行（Act / アクト）        … テストしたい動作を1回だけ行う
                               （ボタンを押す・関数を呼ぶ・APIを叩く）
3. 検証（Assert / アサート）   … 結果が期待どおりかを確かめる
                               （「〜のはず」をチェックし、違えば失敗）
```

> **用語: アサーション（assertion）**
> 「〜であるはずだ」という **主張（断言）** のこと。テストの心臓です。`expect(x).toBe(5)`（フロント）や `self.assertEqual(x, 5)`（バック）のように書き、もし実際の値が主張と違えば、その場でテストは「失敗」になります。

### 1.1 3ステップを日本語の例で

> ※説明用の簡易例（本アプリのコードではありません）

```
【準備】 電卓アプリを開く
【実行】 「2」「＋」「3」「＝」を押す
【検証】 画面に「5」が表示されているはず → 違えば失敗
```

このたった3段で、1つのテストが完成します。`Login.test.tsx` も `test_backend.py` も、すべてこの形の繰り返しです。**「いまどのステップを読んでいるか」を意識すると、テストコードが一気に読みやすくなります。**

## 2. フロントのテスト道具：Vitest と React Testing Library

フロントのテストは、2つの道具を組み合わせて書きます。

> **Vitest（ヴィテスト）とは？**
> JavaScript/TypeScript 用の **テスト実行ツール**（テストランナー）。テストファイルを探して実行し、結果（成功/失敗）をまとめて表示してくれます。`describe`（グループ分け）・`it`（1つのテスト）・`expect`（検証）といった「テストを書くための言葉」を提供します。Vite（ヴィート）というビルドツールと相性がよく、速いのが特徴です。

> **React Testing Library（リアクト・テスティング・ライブラリ。略してRTL）とは？**
> React の画面を **テスト用に仮想で描き**、「画面に○○の文字があるか」「ボタンを押したらどうなるか」を、**ユーザーの視点で** 確認するためのライブラリ。内部の細かい実装ではなく「**人が見て・触って分かること**」を確認するのが思想です。`render`（描く）・`screen`（画面）・`fireEvent`（操作する）などを提供します。

> **なぜ「ユーザーの視点」が大事？**
> 「このボタンの内部関数が呼ばれたか」ではなく「ボタンを押したらエラーが画面に出たか」を確認する方が、**実際の使われ方に近く、壊れに強い** テストになります。内部の作りを変えても、ユーザーから見た振る舞いが同じなら、テストは通り続けるからです。

### 2.1 jsdom ―「ブラウザのふり」をする道具

テストはブラウザではなく **コマンドライン（黒い画面）** で動きます。でも React は本来ブラウザの画面（DOM）を相手にします。そこで **jsdom（ジェイエスドム）** という「ブラウザの画面のふりをするライブラリ」を使い、コマンドライン上に **にせの画面** を用意します。これにより、ブラウザを起動しなくても画面のテストができます（設定は§6で実コードを見ます）。

## 3. モック（にせもの）という考え方

`Login.test.tsx` を読む前に、最重要キーワード **モック** を理解します。

> **モック（mock）とは？**
> テスト対象が依存している「外部のもの」を、**にせもの（替え玉）に差し替える** こと。本物の代わりに、テスト都合のいいように動く偽物を使います。「モック化する」「モックする」と言います。

### 3.1 なぜモックが必要か

ログイン画面 `Login.tsx` は、内部で次の3つに **依存** しています。

1. **API通信**（`api.post(...)` でサーバーへ送る）
2. **画面遷移**（`useNavigate()` で別ページへ移動する）
3. **ロゴ画像**（`import logo from "../../img/TitleRogo.png"`）

テストのときにこれらを本物のまま動かすと、困ったことが起きます。

| 依存 | 本物だと困ること | モックにすると |
|------|------------------|----------------|
| API通信 | テストのたびに本物のサーバーに繋ぐ必要があり、結果も毎回変わる | 「成功を返す/失敗を返す」を **テストが自由に決められる** |
| 画面遷移 | コマンドラインには本物のブラウザ遷移がない | 「遷移しようとしたか・どこへか」を **記録だけする** にせ関数にできる |
| 画像 | テスト環境では画像ファイルを読み込めない | 「`logo.png` という文字列」に置き換えてエラーを避ける |

> **▼ たとえ話：映画の撮影**
> モックは、映画撮影の **スタント（替え玉）や小道具** に似ています。本物の崖から飛び降りる代わりにスタントを使い、本物のお金の代わりに小道具のお札を使います。テストでも「本物だと危険・不便・不安定なもの」を、安全で都合のいいにせものに替えるのです。

### 3.2 Vitest でモックする道具

| 書き方 | 意味 |
|--------|------|
| `vi.fn()` | **にせの関数**（モック関数）を作る。呼ばれた回数や引数を記録してくれる |
| `vi.mock("モジュール名", () => ...)` | あるモジュール（ファイル）丸ごとを、にせものに差し替える |
| `xxx.mockResolvedValueOnce(値)` | 「次の1回だけ、**成功**してこの値を返す」ように仕込む（API成功を演じる） |
| `xxx.mockRejectedValueOnce(値)` | 「次の1回だけ、**失敗**してこのエラーを投げる」ように仕込む（API失敗を演じる） |
| `vi.clearAllMocks()` | モックの記録（呼ばれた回数など）を **全部リセット** する |

これだけ頭に入れたら、いよいよ実コードを読みます。

## 4. 実コード全解説：Login.test.tsx 全132行

ここが本章フロント編の核心です。本アプリのログイン画面のテスト `frontend/src/tests/MainPage/Login.test.tsx` を、**1行残らず** 読みます。このファイルには「成功・失敗・401遷移・別エラー」という4つの代表テストが詰まっており、**フロントのテストの型がすべて入っています**。

### 4.1 インポート部（1〜5行目）

> **▼ このコードがやること（先に日本語で）:** テストを書くのに必要な道具を、各ライブラリから読み込みます。Vitest の言葉（describe など）、RTL の道具（render など）、ブラウザのふりをする道具、そしてテスト対象の `Login` 画面本体を取り込みます。

```tsx
// ① Vitestの道具を読み込む
import { vi, describe, it, expect, beforeEach } from "vitest";
// ② RTLの道具を読み込む
import { render, screen, fireEvent, waitFor } from "@testing-library/react";
// ③ テスト用のルーター（後述）
import { MemoryRouter } from "react-router-dom";
// ④ 「画面に○○がある」を確認する追加機能
import "@testing-library/jest-dom/vitest";
// ⑤ テスト対象＝ログイン画面本体
import Login from "../../MainPage/Login";
```

1行ずつ見ます。

- **① `import { vi, describe, it, expect, beforeEach } from "vitest";`**
  Vitest から5つの道具を取り出します。
  - `vi` … モックを作る道具（§3）。
  - `describe` … テストを **グループにまとめる** 箱。
  - `it` … **1つのテスト** を書く単位（「〜であること」と読む）。
  - `expect` … **検証**（アサーション）を書く道具。
  - `beforeEach` … 各テストの **前に毎回** 実行する準備処理。

- **② `import { render, screen, fireEvent, waitFor } from "@testing-library/react";`**
  RTL から4つの道具を取り出します。
  - `render` … React の画面を **テスト用に描く**（仮想画面に表示する）。
  - `screen` … 描かれた **画面（仮想DOM）全体** を表すオブジェクト。ここから要素を探します。
  - `fireEvent` … クリックや入力など、**ユーザー操作を発火** させる道具。
  - `waitFor` … 「ある条件が満たされるまで **待つ**」道具（非同期処理の完了待ち）。

- **③ `import { MemoryRouter } from "react-router-dom";`**
  `MemoryRouter`（メモリールーター）は、テスト専用の **にせのルーター（経路管理）**。本物のルーターはブラウザのURLを使いますが、テストにはブラウザのURLがありません。そこで「メモリ上だけで動くルーター」で `Login` を包みます。

  > **なぜ？** `Login.tsx` の中には `<Link to="/help">`（リンク）や `useNavigate()`（遷移）が入っています。これらは「ルーターの中で使う」ことが前提なので、ルーター無しで描こうとするとエラーになります。`MemoryRouter` で包むことで、ルーターがある状態を再現します。

- **④ `import "@testing-library/jest-dom/vitest";`**
  jest-dom（ジェスト・ドム）という追加機能を読み込みます。これにより `toBeInTheDocument()`（画面に存在するか）や `toHaveTextContent()`（この文字を含むか）といった、**画面チェック専用の便利な検証** が使えるようになります。`/vitest` を付けるのは「Vitest向けに登録する」という意味です。

- **⑤ `import Login from "../../MainPage/Login";`**
  **テストの主役**、ログイン画面本体を読み込みます。`../../` は「2つ上のフォルダ」。テストファイルは `src/tests/MainPage/` にあり、本体は `src/MainPage/` にあるので、2階層上がって `MainPage/Login` を指します。

### 4.2 画像のモック（7〜8行目）

> **▼ このコードがやること:** ロゴ画像の読み込みを、にせもの（ただの文字列 `"logo.png"`）に差し替えます。テスト環境では本物の画像ファイルを処理できないため、エラーを防ぐ目的です。

```tsx
// モック設定
// 画像 import を文字列に置き換える
vi.mock("../../img/TitleRogo.png", () => ({ default: "logo.png" }));
```

- **`vi.mock("../../img/TitleRogo.png", () => ({ default: "logo.png" }));`**
  「`Login.tsx` が `import logo from "../../img/TitleRogo.png"` で画像を読み込もうとしたら、**本物の画像の代わりに `{ default: "logo.png" }` を渡せ**」という指示です。
  - `() => ({ default: "logo.png" })` … 「`default` という名前で `"logo.png"` を返す」関数。
  - `import logo from "..."` の `logo` には、この `default` の値（＝文字列 `"logo.png"`）が入ります。

  > **なぜ `default` なの？** `import 名前 from "..."`（デフォルトインポート）で受け取る値は、モジュールの `default` というキーに入ります。だからモックも `default` で返す必要があります。画像は本来「画像ファイルへのパス（文字列）」として扱われるので、にせの文字列で十分です。

### 4.3 API（axios）のモック（10〜19行目）

> **▼ このコードがやること:** API通信を担当する `api/axios` というモジュールを、丸ごと「にせの通信」に差し替えます。get/post/put/delete の4メソッドを、それぞれ「呼ばれたことを記録するだけのにせ関数」にします。さらに、そのにせモジュールを `mockedApi` という名前で取り出して、後でテストごとに「成功を返せ／失敗を返せ」と仕込めるようにします。

```tsx
// api/axios モジュールを丸ごと差し替え
vi.mock("../../api/axios", () => ({
  //   default エクスポート（import api from で受け取る対象）
  default: {
    //   get を にせ関数に
    get: vi.fn(),
    //   post を にせ関数に（ログインで使う主役）
    post: vi.fn(),
    //   put を にせ関数に
    put: vi.fn(),
    //   delete を にせ関数に
    delete: vi.fn(),
  },
}));
// 差し替え後の（にせの）api を取り込む
import api from "../../api/axios";
// 型を any にして mockResolvedValueOnce 等を呼べるように
const mockedApi = api as any;
```

1行ずつ。

- **`vi.mock("../../api/axios", () => ({ default: { ... } }))`**
  本アプリの通信モジュール `api/axios`（`07`章で見た axios の設定済みインスタンス）を、丸ごとにせものに置き換えます。`default` の中に4つのメソッドを用意します。

- **`get: vi.fn()` / `post: vi.fn()` / `put: vi.fn()` / `delete: vi.fn()`**
  それぞれ `vi.fn()`（にせの関数）にします。にせ関数は **呼ばれた回数・引数を記録** し、後から「何を返すか」を仕込めます。ログインで実際に使うのは `post`（従業員番号をサーバーへ送る）です。残り3つも、`Login.tsx` が間接的に読み込んでもエラーにならないよう、念のため用意しています。

- **`import api from "../../api/axios";`**
  `vi.mock` で差し替えた **にせの** `api` を取り込みます。`vi.mock` は「このファイルの中で `api/axios` を読み込むものは全部にせものになる」効果があるので、ここで取り込む `api` も自動的ににせものです。

### 4.4 axios本体のモック（21〜25行目）

> **▼ このコードがやること:** axios の `isAxiosError`（このエラーは通信由来のエラーか？を判定する関数）を、にせものに差し替えます。`Login.tsx` のエラー処理がこの関数を使うため、テストでも動くようにします。

```tsx
// axios本体を差し替え

  default: {
    // 「err に response があれば通信エラー」とみなす にせ実装

```

- **`isAxiosError: vi.fn((err) => !!err.response)`**

  > **なぜモックする？** `Login.tsx` は「APIエラーが起きたとき、それが通信エラーなら `err.response.status`（401など）を見て分岐する」処理を持っています。その分岐に使う `isAxiosError` を、テストでコントロールできるよう、にせの判定に置き換えています。後のテスト（4.10・4.11）で、わざと `response` を持つエラーを投げて「通信エラー扱い」にさせます。

### 4.5 画面遷移（navigate）のモック（27〜31行目）

> **▼ このコードがやること:** 画面遷移を行う `useNavigate()` を、にせの遷移関数 `mockedNavigate` に差し替えます。これにより「`Login.tsx` がどこへ遷移しようとしたか」をテストが記録・検査できます。

### 4.6 テストのグループと共通準備（33〜36行目）

> **▼ このコードがやること:** 「Login Component」という名前で、これから書く全テストを1つのグループにまとめます。さらに、各テストが始まる前に毎回「モックの記録をリセット」して、前のテストの影響が残らないようにします。

```tsx
// 「Login Component」というテストグループの開始
describe("Login Component", () => {
  // 各テストの実行前に、毎回これを行う
  beforeEach(() => {
    //   モックの呼び出し記録を全部リセット
    vi.clearAllMocks();
  });
```

- **`describe("Login Component", () => { ... })`**
  `describe`（ディスクライブ）は **テストの章立て**。中に複数の `it`（テスト1件）を入れ、まとめて「Login Component のテスト群」とします。実行結果でも「Login Component」という見出しの下に各テストが並びます。

- **`beforeEach(() => { ... })`**
  `beforeEach`（ビフォアイーチ）は「**各テストの直前に毎回** 走る準備処理」。

- **`vi.clearAllMocks();`**
  すべてのモックの **記録（呼ばれた回数・引数・仕込んだ戻り値）を消去** します。
  > **なぜ毎回リセット？** テストは **互いに独立** であるべきです。もし前のテストで `mockedNavigate` が呼ばれた記録が残ったままだと、次のテストで「遷移したか？」を調べたとき、前の記録に引きずられて誤判定します。毎回まっさらにすることで、各テストが「ゼロから」始まり、**順番や他テストの影響を受けない** のが保証されます。これはテストの鉄則です。

## 5. getBy / findBy / queryBy の使い分け

§4で `getByRole` `getByLabelText` `findByRole` が出てきました。RTL の要素取得には **3つの系統** があり、使い分けが超重要です。

| 系統 | 待つ？ | 見つからないとき | 主な用途 |
|------|--------|------------------|----------|
| **`getBy...`** | 待たない（即取得） | **すぐエラー（失敗）** | 「最初から画面にあるはず」の要素 |
| **`findBy...`** | **待つ**（非同期） | しばらく待って無ければエラー | 「後から現れる」要素（API後に出るエラー等） |
| **`queryBy...`** | 待たない | **`null` を返す**（エラーにしない） | 「無いはず」を確認したいとき |

### 5.1 図で覚える

```
getBy   … 「今ここにある？」即チェック。無ければ即・赤エラー
findBy  … 「現れるまで待つよ」少しずつ何度も探す。時間切れで赤エラー
queryBy … 「あるか無いか教えて」無くても怒らず null を返す
```

### 5.2 本アプリでの実例での使い分け

- **`screen.getByLabelText("従業員番号")`**（§4.7④, 4.8④…）
  入力欄は **画面を描いた瞬間から存在** します。だから「待たない」`getBy` でOK。

- **`screen.getByRole("button", { name: "ログイン" })`**（§4.8⑥…）
  ボタンも最初からあります。`getBy` でOK。

- **`screen.findByRole("alert")`**（§4.9④, 4.11④）
  エラー表示は **ログイン失敗の後にやっと現れます**。最初は無いので、`getBy` だと「無い！」と即失敗します。`findBy` で「現れるまで待つ」のが正解。

> **使い分けの早見フレーズ**
> 「**最初からある → getBy**」「**後から出る → findBy**」「**無いことを確かめる → queryBy**」。この3つを覚えれば、RTLの要素取得で迷いません。

> **⚠️ よくある失敗:** API後に出るエラーを `getByRole("alert")` で取ろうとして、毎回「要素が見つからない」で落ちる。これは `findByRole`（待つ）に変えれば直ります。逆に、最初からある要素を `findBy` で取っても動きますが、無駄に待つので `getBy` が適切です。

## 7. バックのテスト道具：Django TestCase と APIClient

ここからバックエンド（Django/Python）のテストに移ります。考え方（3ステップ・モック）は同じですが、道具が変わります。

> **Django TestCase（テストケース）とは？**
> Django が用意する **テスト用の土台クラス**。これを継承（`07`章の「親クラスを引き継ぐ」）してテストを書きます。最大の特徴は、**各テストの前に「まっさらなテスト用データベース」を用意し、テスト後に元に戻す** こと。本物のデータを汚さず、各テストが独立して動きます。

> **APIClient（エーピーアイ・クライアント）とは？**
> Django REST Framework が用意する **にせのブラウザ**。`self.client.get('/api/...')` や `self.client.post('/api/...')` と書くと、サーバーを起動せずに **アプリの中で直接APIを呼べます**。フロントの `fireEvent`（操作を発火）に相当する、「APIを叩く道具」です。

### 7.1 フロントとバックの道具の対応表

| やりたいこと | フロント（Vitest/RTL） | バック（Django） |
|--------------|------------------------|------------------|
| テストのグループ | `describe(...)` | `class TestXxx(TestCase):`（クラス） |
| 1つのテスト | `it("...", () => {})` | `def test_xxx(self):`（メソッド） |
| 各テスト前の準備 | `beforeEach(...)` | `def setUp(self):` |
| 操作する/呼ぶ | `fireEvent` / `render` | `self.client.get/post/...` |
| 検証する | `expect(x).toBe(...)` | `self.assertEqual(x, ...)` |

> **覚え方:** Django のテストは「**クラスがグループ、`test_` で始まるメソッドが1テスト、`setUp` が準備、`assertXXX` が検証**」。この4点セットで読めます。

### 8.2 共通ヘルパー：make_break_times（27〜35行目）

> **▼ このコードがやること:** 社員を作るときに必須の「休憩時間」フィールドを、まとめて一気に用意するための補助関数です。社員1人につき休憩時間の項目が大量にあるため、毎回手で書くと大変なので、関数で生成します。

```python
def make_break_times():
    # 必須の break_time 一式を作る補助関数
    """Helper to generate all required break_time fields."""
    # ① 空の辞書（キー:値の入れ物）を用意
    bt = {}
    # ② 1〜6 まで繰り返す（直＝シフトが6種）
    for i in range(1, 7):
        # ③ break_time1〜6 に基本休憩を設定
        bt[f'break_time{i}'] = '#10401130'
        # ④ 残業休憩1
        bt[f'break_time{i}_over1'] = '#15101520'
        # ⑤ 残業休憩2
        bt[f'break_time{i}_over2'] = '#20202110'
        # ⑥ 残業休憩3
        bt[f'break_time{i}_over3'] = '#01400150'
    # ⑦ 出来上がった辞書を返す
    return bt
```

1行ずつ。

- **① `bt = {}`** … 空の **辞書（dictionary）** を用意。辞書は「キー → 値」の対応表（`04`章相当）。
- **② `for i in range(1, 7):`** … `i` を 1, 2, 3, 4, 5, 6 と変えながら繰り返す。`range(1, 7)` は「1以上7未満」＝1〜6。本アプリは勤務形態（直＝シフト）が6種類あるため、それぞれに休憩時間があります（`member` モデル）。
- **③〜⑥** … `f'break_time{i}'` の `f'...{i}...'` は **f文字列**。`i` の値を文字列に埋め込みます。`i=1` のとき `'break_time1'`、`i=2` のとき `'break_time2'`…と、キー名が自動生成されます。値の `'#10401130'` は「10:40〜11:30 が休憩」を表す本アプリ独自の符号（`#` ＋ 開始時刻 ＋ 終了時刻、`08`章の工数ロジック相当）。
- **⑦ `return bt`** … 完成した辞書（`break_time1`〜`break_time6` と各 `over1〜3`、合計24項目）を返す。

> **なぜヘルパー関数にする？** 社員を作るたびに24個の休憩項目を手で書くのは大変で、ミスも出ます。1つの関数にまとめておけば、`**make_break_times()` の1行で全項目を渡せます（`**` の意味は次の §8.3⑦で説明）。**「繰り返す準備は関数化する」** は、テストを読みやすく・壊れにくくする定石です。

### 8.3 共通土台：BaseTestCase の setUp（38〜60行目）

> **▼ このコードがやること:** ほとんどのテストが共通で使う「前提データ」をまとめて用意する土台クラスです。にせのブラウザ・管理者設定・工数バージョン・管理者社員・一般社員を、各テストの前に毎回作ります。

            kosu_name='TestVer', kosu_title_1='作業A'
        )

        # ⑥ 休憩時間一式を生成（§8.2）

        self.member = member.objects.create(

        )

            authority=False, administrator=False, **break_times

```

1行ずつ。

- **① `class BaseTestCase(TestCase):`**
  `TestCase` を **継承** した「共通の親クラス」。これ自体はテストを持たず、**他のテストクラスがこれを継承して使う土台** です（`class TestModels(TestCase)` ではなく `class TestLoginLogout(BaseTestCase)` のように）。共通準備を1か所に集約する設計。

- **② `def setUp(self):`**
  `setUp`（セットアップ）は、フロントの `beforeEach`（§4.6）に相当。**各テストメソッドの直前に毎回** 自動で呼ばれ、前提データを整えます。
  > **なぜ毎回？** TestCase は各テストの後にDBを巻き戻す（リセットする）ので、毎回ここで前提を作り直さないと、データが空のままテストが始まってしまうからです。各テストが「同じきれいな前提」から始まる保証になります。

- **③ `self.client = APIClient()`**
  にせのブラウザを用意し、`self.client` に持たせます。以後 `self.client.get(...)` でAPIを叩けます。`self.` を付けると、同じテストクラスの他のメソッドから使い回せます。

- **④ `self.admin_settings = administrator_data.objects.create(menu_row='20')`**
  管理者設定（`administrator_data` モデル）を **1件作成**。`objects.create(...)` は「この内容でDBに1行作る」Djangoの書き方（`06`章）。`menu_row='20'` はメニュー表示行数などの設定値。作った結果を `self.admin_settings` に持たせ、後のテストで使います。

- **⑤ `self.division = kosu_division.objects.create(kosu_name='TestVer', kosu_title_1='作業A')`**
  工数の定義バージョン（`kosu_division`）を1件作成。コメント `# needed for login` のとおり、ログイン処理がこのバージョン情報を参照するため、**ログインを通すための前提** として用意します。

- **⑥ `break_times = make_break_times()`**
  §8.2 のヘルパーで、休憩時間24項目の辞書を作ります。

- **⑦ `self.member = member.objects.create(employee_no=12345, ..., authority=True, administrator=True, **break_times)`**
  **管理者権限つきの社員** を作成。
  - `employee_no=12345` … 従業員番号（フロントのテストでも使った番号と同じ）。
  - `authority=True` … 「一般の管理機能を使える権限あり」。
  - `administrator=True` … 「最上位の管理者である」。
  - `**break_times` … **辞書を「キー=値」の引数群に展開** する書き方（`**` ＝アンパック）。`break_time1='#10401130', break_time2=..., ...` と24個分を一気に渡すのと同じになります。これが §8.2 でヘルパーを作った狙いです。

  > 辞書を関数の **キーワード引数** にバラして渡す書き方。`{'a':1, 'b':2}` に `**` を付けると `a=1, b=2` として渡されます。大量の引数を1行でスッキリ渡せます。

- **⑧ `self.normal_member = member.objects.create(employee_no=99999, ..., authority=False, administrator=False, **break_times)`**
  **権限のない一般社員** を作成。`authority=False`・`administrator=False` がポイント。

### 8.4 ログイン補助メソッド（62〜75行目）

> **▼ このコードがやること:** テストの中で「ログインした状態」を作るための補助メソッドです。多くのAPIはログイン必須なので、これを呼んでセッションを確立してから本題のAPIを叩きます。

```python
    # ① 指定番号でログインする補助
    def login(self, employee_no=12345):
        """Helper to set session via login endpoint."""
        # ② ログインAPIをPOSTで叩く
        response = self.client.post(
            #    ログインのURL
            '/api/login/',
            # ③ 従業員番号をJSON文字列にして送る
            json.dumps({'employee_no': employee_no}),
            # ④ 「JSONを送る」と宣言
            content_type='application/json'
        )
        # ⑤ 応答を返す
        return response

    # ⑥ 管理者(12345)でログインする近道
    def login_as_admin(self):
        return self.login(12345)

    # ⑦ 一般(99999)でログインする近道
    def login_as_normal(self):
        return self.login(99999)
```

1行ずつ。

- **① `def login(self, employee_no=12345):`**
  ログインを行う補助メソッド。引数 `employee_no=12345` は **デフォルト値つき**。何も指定しなければ管理者番号 12345 でログインします。

- **② `response = self.client.post('/api/login/', ..., content_type='application/json')`**
  にせのブラウザで、ログインAPI `/api/login/` を **POST** で叩きます（`07`章のPOST：データを送る通信）。フロントの `Login.tsx` がやっているのと同じことを、テスト内で再現しています。

- **③ `json.dumps({'employee_no': employee_no})`**
  `{'employee_no': 12345}` という辞書を、**JSON文字列** に変換します。`json.dumps`（ダンプス）は「Pythonの辞書 → JSON文字列」の変換関数。サーバーへはJSON形式の文字列で送るためです。

- **④ `content_type='application/json'`**
  「いま送るデータはJSON形式ですよ」とサーバーに宣言するヘッダ。これがないとサーバーが中身を正しく解釈できません。

- **⑤ `return response`** … サーバーの応答を返します。呼び出し側で「ログインが成功したか（status 200か）」などを検査できます。

- **⑥⑦ `login_as_admin` / `login_as_normal`**
  それぞれ「管理者でログイン」「一般でログイン」の **近道メソッド**。`self.login(12345)` / `self.login(99999)` を呼ぶだけ。テスト本文で `self.login_as_admin()` と書けば、意図（管理者として操作）が一目で分かります。

> **なぜログイン補助を用意する？** ほとんどのAPIは「ログイン済み」が前提（CLAUDE.mdの「Session-based authentication」）。各テストで毎回ログイン手順を書くと冗長なので、1メソッドにまとめます。`self.login_as_admin()` の1行で「ログイン状態」を作れるので、各テストは **本題の検証に集中** できます。

> **▼ このコードがやること:** タスク記録（AsyncTask）を上限を超えて作ったとき、「古いものが自動で消えて、件数が上限以内に収まる」というルールが守られているかを確認します。単なる作成ではなく「**しくみのふるまい**」をテストする例です。

## 10. APIの 401 / 403 / 200 を確かめるテストの考え方

`test_backend.py` の中核は **「APIが正しい権限チェックをするか」** のテストです。ここがバックテストの最重要ポイントなので、考え方を整理します。

### 10.1 3つのステータスの意味

| ステータス | 意味 | いつ返る |
|------------|------|----------|
| **200 OK** | 成功 | ログイン済み・権限ありで、正しくデータが返るとき |
| **401 Unauthorized** | 未認証 | **ログインしていない**（セッションが無い）とき |
| **403 Forbidden** | 権限不足 | ログイン済みだが、**その操作の権限が無い** とき |

> **401と403の違い（重要）**
> - **401** ＝「**あなたが誰か分からない**」。ログインしていない状態。→ ログイン画面へ。
> - **403** ＝「**あなたが誰かは分かるが、これをする権限が無い**」。ログイン済みの一般ユーザーが、管理者専用機能を触ったときなど。
>
> たとえ話：401は「**入館証を持たずにビルに入ろうとした**」（そもそも誰か不明）。403は「**入館証はあるが、社長室には入れない**」（身元は分かるが権限不足）。

    #    応答に 'admin_data' が含まれるか
    self.assertIn('admin_data', response.data)
```

- **②** `self.login_as_admin()` で **先にログイン** してからGET。今度は **200**（成功）になり、さらに `response.data`（応答の中身）に `'login_data'` `'admin_data'` というキーが含まれることを `assertIn` で確認。「正しくデータを返すか」まで見ています。

```python
# ③ 権限なしユーザーが権限要メニューへ
def test_member_menu_without_authority(self):
    #    一般ユーザーでログイン
    self.login_as_normal()
    #    権限が必要なメニューにGET
    response = self.client.get('/api/member_menu/')
    #    → 403（権限不足）
    self.assertEqual(response.status_code, 403)
```

- **③** **一般ユーザー** で（`login_as_normal`）、人員管理メニュー（管理者権限が要る）にアクセス。`authority=False` なので **403** が返るはず。「権限の無い人を弾く」を保証します。

> **この3点セットがAPIテストの王道**
> 1つのAPIに対して「**未ログイン→401**」「**正しい権限→200**」「**権限不足→403**」の3テストを書く。これで「認証と権限のガードが効いているか」が完全に守られます。`test_backend.py` 全体が、ほぼこの型の繰り返しでできています（メニュー・人員・工数・定義・問い合わせ・管理者…すべてに対して）。

### 10.3 実例：作成・更新・削除の検証（298〜381行目より）

権限だけでなく「データ操作が正しく行われたか」も検証します。`TestMemberViews` から。

```python

    self.login_as_admin()
    # ② 送る社員データ

        'employee_no': 55555, 'name': '新規太郎', 'shop': 'P',
        'authority': False, 'administrator': False,

- **③ `self.client.post('/api/member_new/', data, format='json')`**
  社員作成APIをPOSTで叩く。`format='json'` で「JSONとして送る」（§8.4③の `json.dumps` の簡単版。APIClientがやってくれます）。
- **④ `self.assertEqual(response.status_code, 201)`**
  **201 Created**（新規作成成功のステータス）を確認。200と区別し、「新しく作られた」ことを表します。
- **⑤ `self.assertTrue(member.objects.filter(employee_no=55555).exists())`**
  `assertTrue(x)` は「`x` が **真（True）** を期待」。「従業員番号55555の社員が **実際にDBに存在する**」ことを確認。APIが200を返すだけでなく、**本当にデータが作られたか** までチェックするのが堅実なテストです。

```python

> **作成は201・削除は204・取得や更新は200**。HTTPステータスを正しく確認することで、APIの「契約」を守れます（`07`章のステータスコード）。

## 11. assertXXX メソッド早見表

ここまでに出てきた検証メソッドを一覧にします。バックテスト（Django/unittest）の `self.assertXXX(...)` 系です。

| メソッド | 意味（〜を期待する） | 例 |
|----------|----------------------|----|
| `assertEqual(a, b)` | a と b が **等しい** | `assertEqual(str(m), '山田太郎')` |
| `assertNotEqual(a, b)` | a と b が **等しくない** | |
| `assertTrue(x)` | x が **真（True）** | `assertTrue(...exists())` |
| `assertFalse(x)` | x が **偽（False）** | `assertFalse(...exists())` |
| `assertIn(a, b)` | a が b に **含まれる** | `assertIn('login_data', response.data)` |
| `assertNotIn(a, b)` | a が b に **含まれない** | |
| `assertIsNone(x)` | x が **None（無）** | `assertIsNone(err)` |
| `assertIsNotNone(x)` | x が **None でない** | `assertIsNotNone(err)` |
| `assertLessEqual(a, b)` | a ≤ b（a が b 以下） | `assertLessEqual(count, MAX)` |
| `assertGreaterEqual(a, b)` | a ≥ b（a が b 以上） | `assertGreaterEqual(week, 1)` |
| `assertRaises(例外)` | 中の処理が **その例外を投げる** | `with self.assertRaises(ValueError):` |

> **`assertRaises` の使い方（1219行目あたりの例）**
> ```python
> with self.assertRaises(ValueError):          # この中で ValueError が起きることを期待
>     parse_break_time(None, '...', jst)        # None を渡すとエラーになるはず
> ```
> 「**わざと不正な入力を与え、ちゃんとエラーになるか**」を確認するテスト。`with` ブロックの中で指定の例外が起きれば成功、起きなければ「エラーになるべきなのにならなかった」で失敗します。**異常系（エラーになるべき場合）のテスト** に使います。

### 11.1 フロントの expect 系との対応

| フロント（Vitest/jest-dom） | バック（Django） | 意味 |
|------------------------------|------------------|------|
| `expect(a).toBe(b)` | `assertEqual(a, b)` | 等しい |
| `expect(x).toBeTruthy()` | `assertTrue(x)` | 真 |
| `expect(x).toBeFalsy()` | `assertFalse(x)` | 偽 |
| `expect(el).toBeInTheDocument()` | （DOM特有・フロントのみ） | 画面に存在 |
| `expect(el).toHaveTextContent(s)` | `assertIn(s, ...)` | 文字を含む |
| `expect(fn).toHaveBeenCalledWith(x)` | （モック特有） | x で呼ばれた |

> **本質は同じ:** フロントもバックも「**期待を書いて、違えば失敗**」というアサーションの考え方は完全に共通です。書き方（`expect(...).toBe(...)` か `self.assertEqual(...)` か）が違うだけです。

## 12. バックのテスト設定（test_settings.py）

バックのテストは、本番とは **別の設定** で動かします。`hozen_another/test_settings.py`（全31行）を読みます。

> **▼ このコードがやること:** テスト専用の設定です。本番設定を引き継ぎつつ、(1) DBをメモリ上の使い捨てSQLiteに、(2) 非同期処理を即時実行に、(3) マイグレーションを省略、に切り替えます。テストを速く・安全に・独立して動かすための工夫です。

```python
# ① 本番設定をすべて引き継ぐ
from .settings import *

# ② DBの設定を上書き
DATABASES = {
    'default': {
        #    SQLiteを使う（PostgreSQLでなく）
        'ENGINE': 'django.db.backends.sqlite3',
        #    メモリ上のDB（ファイルに残さない）
        'NAME': ':memory:',
    }
}

# Disable signals during tests to avoid side effects
# ③ 「今はテスト中」フラグ（副作用を抑える目印）
TESTING = True

# Disable django-q cluster requirement for tests
# ④ 非同期タスクの設定
Q_CLUSTER = {
    'name': 'test',
    #    'sync': True ＝ 非同期処理を「その場で即実行」
    'sync': True,
    'timeout': 60,
    'orm': 'default',
}

# Custom test runner that creates tables from models directly (bypasses migrations)
# ⑤ マイグレーションを無効化する仕掛け
class DisableMigrations:
    """Fake migration module that tells Django to skip migrations and use syncdb."""
    def __contains__(self, item):
        return True
    def __getitem__(self, item):
        return None

# ⑥ マイグレーションを飛ばし、モデルから直接表を作る
MIGRATION_MODULES = DisableMigrations()
```

要点を1つずつ。

- **① `from .settings import *`**
  本番の設定（`settings.py`）を **まるごと取り込み**、その上で必要な箇所だけ上書きします。「本番とほぼ同じ環境で、テストに都合の悪い部分だけ変える」やり方。

- **② DATABASES を `sqlite3` の `:memory:` に上書き**
  本番は PostgreSQL（CLAUDE.md）ですが、テストでは **SQLite のメモリDB** を使います。
  > **なぜ？** メモリ上のDBは **超高速** で、テストが終われば **跡形もなく消える**。本物のDBを汚す心配がなく、毎回まっさらから始められます。テストの「速さ」と「安全（独立性）」の両立です。

- **③ `TESTING = True`**
  「いまテスト中」という目印。本体コードはこのフラグを見て、テスト中は不要な副作用（メール送信や外部通知など）を抑制できます。コメントの「Disable signals」が示すとおり、シグナル（モデル変更時の自動処理。CLAUDE.mdの `signals.py`）の暴発を防ぐためにも使われます。

- **④ `Q_CLUSTER` の `'sync': True`**
  本アプリは Django-Q で **非同期タスク**（バックアップ等）を裏で動かします（CLAUDE.md）。テストでは `'sync': True` にして、非同期タスクを **その場で即時実行** させます。
  > **なぜ？** テストで「裏で後から実行される」と、結果を待てず検証できません。`sync: True` で「呼んだら即その場で実行」にすると、結果をすぐ検証できます。フロントの「モック」と同じ発想（テスト都合に合わせる）です。

- **⑤⑥ `DisableMigrations` でマイグレーションを飛ばす**
  通常、DBの表はマイグレーション（`06`章の `makemigrations`/`migrate`）で作ります。テストでは、それを飛ばして **モデル定義から直接、表を作ります**。
  > **なぜ？** コメントにあるとおり、PostgreSQL では許される書き方（`max_length` 無しの文字列フィールド等）が SQLite では問題になることがあるため、マイグレーションを経由せず「モデルから直接」表を作って回避しています。これにより、メモリ上の SQLite でもテストが安定して動きます。

> **要するに test_settings.py は:** 「本番と似た設定のまま、**DBを使い捨て・処理を即時・準備を最速** に切り替えて、テストを高速・安全・独立に回すための専用設定」です。だから実行時に `--settings=hozen_another.test_settings` で **この設定を指定** します（次の §13）。

## 14. テストが失敗したときの読み方と対応

テストが赤くなったら、慌てず **メッセージを読む** のが鉄則です。テストは「どこが・どう期待と違ったか」を必ず教えてくれます。

### 14.1 バックの失敗メッセージの読み方

> ※説明用の簡易例（実際の失敗出力の典型）

```
======================================================================
FAIL: test_member_creation_and_str (kosu.tests.test_backend.TestModels)
----------------------------------------------------------------------
Traceback (most recent call last):
  File ".../test_backend.py", line 88, in test_member_creation_and_str
    self.assertEqual(str(m), '山田太郎')
AssertionError: 'member object (1)' != '山田太郎'
----------------------------------------------------------------------
```

読み解き方：

1. **`FAIL: test_member_creation_and_str`** … どのテストが落ちたか（名前で分かる）。
2. **`line 88, in ...`** … どの行で落ちたか。
3. **`self.assertEqual(str(m), '山田太郎')`** … どの検証で落ちたか。
4. **`AssertionError: 'member object (1)' != '山田太郎'`** … **期待と実際の違い**。「実際は `'member object (1)'` だったが、`'山田太郎'` を期待していた（`!=`＝等しくない）」。

→ ここから「`member` モデルの `__str__`（文字列表現）が壊れている（名前を返していない）」と推理できます。**実際の値が左、期待が右** に並ぶことが多いので、その差分を見ます。

### 14.2 フロントの失敗メッセージの読み方

> ※説明用の簡易例

```
 FAIL  src/tests/MainPage/Login.test.tsx > Login Component > ログイン成功時に / へ遷移すること
AssertionError: expected "mockedNavigate" to be called with arguments: [ '/' ]

Number of calls: 0
```

- どのテストが落ちたか（`>` でグループ＞テスト名）。
- `expected ... to be called with [ '/' ]` … 「`/` で呼ばれることを期待した」。
- `Number of calls: 0` … 「実際は **0回** 呼ばれた」＝遷移していない。

→「クリックしても遷移していない」。原因候補は「モックの仕込み忘れ」「`waitFor` で待たずに即検証して早すぎた」「本体の成功判定の条件が変わった」など。

### 14.3 失敗時の対応フロー

```
1. メッセージを読む       … どのテスト・どの行・期待と実際の差は？
2. 「テストが正しい」か    … 仕様変更でテストの方を直すべき場合もある
   「本体が壊れた」か を判断
3a. 本体が壊れた          → 本体コードを直す（テストは正しい仕様の証）
3b. 仕様が変わった        → テストを新仕様に合わせて更新する
4. 再実行して緑になるまで  … 1つ直すごとに流し直す
```

> **⚠️ やってはいけないこと:** 失敗したテストを **理解せずに消す・コメントアウトする**。それは「健康診断で異常が出たから検査項目を削った」のと同じで、本当の不具合を見逃します。**まず原因を理解** してから、本体を直すかテストを直すかを判断します。

> **なぜテストの方を直すこともある？** 仕様が正式に変わったとき（例：成功時の遷移先が `/` から `/home` に変更）、古いテストは「`/` を期待」のままなので落ちます。この場合はテストを新仕様（`/home`）に更新するのが正解。**テストは「現在の正しい仕様」を映す鏡** なので、仕様が変われば一緒に更新します。

## 15. 新しいテストの足し方

機能を追加・修正したら、テストも足すのが理想です。**既存のテストをコピーして一部を変える** のが最速・最安全です。

### 15.1 フロントに1つ足す（型をなぞる）

`Login.test.tsx` のテスト2（§4.8）をコピーし、「番号が空のときボタンを押してもAPIを呼ばないこと」を確かめる例を作るなら、こう考えます。

> ※説明用の簡易例（足し方のイメージ）

```tsx
// ① 新しい仕様を名前に
it("従業員番号が空ならログインAPIを呼ばないこと", () => {
  // ② 準備：描く
  render(
    <MemoryRouter>
      <Login />
    </MemoryRouter>
  );
  // ③ 実行：空のままクリック
  fireEvent.click(screen.getByRole("button", { name: "ログイン" }));
  // ④ 検証：postは呼ばれていないはず
  expect(mockedApi.post).not.toHaveBeenCalled();
});
```

- 既存テストの「`render` → `fireEvent` → `expect`」の骨格をそのまま流用し、**仕込みと検証だけ** を目的に合わせて変えます。
- `expect(...).not.toHaveBeenCalled()` … `not` を挟むと「**呼ばれていないことを期待**」になります。

> **注:** これは「足し方の型」を示す説明用の例です。実際に追加する際は、`Login.tsx` の本当の挙動（空欄時に `required` でブラウザが送信を止めるか等）を確認して、テストが実態と合うようにします。

### 15.2 バックに1つ足す（型をなぞる）

`test_backend.py` の §10.2 のパターンをコピーし、新しいAPIに「未ログイン→401」を足すなら：

> ※説明用の簡易例

```python
# ① 新APIの未ログインテスト
def test_new_api_without_login(self):
    # ② ログインせずGET
    response = self.client.get('/api/new_endpoint/')
    # ③ 401を期待
    self.assertEqual(response.status_code, 401)
```

- 既存の `test_menu_get_without_login`（§10.2①）と **ほぼ同じ形**。URLだけ新しいAPIに変えます。
- `BaseTestCase` を継承したクラスに置けば、`self.client` や `self.login_as_admin()` がそのまま使えます。

### 15.3 テストを足す手順まとめ

```
1. 似た既存テストを見つける          … 同じ種類（表示/成功/権限…）を探す
2. それをコピーして名前を変える       … it("...") / def test_xxx の名前
3. 準備（仕込み）を目的に合わせる     … mock... / data = {...}
4. 実行を目的に合わせる              … 操作する要素・叩くURL
5. 検証を目的に合わせる              … expect / assert の期待値
6. 流して緑になるか確認              … npm run test:run / python manage.py test ...
```

> **黄金ルール:** 「**バグを直したら、そのバグを再現するテストを1つ足す**」。これで「同じバグが二度と戻ってこない（リグレッションしない）」ことが保証されます。本アプリの `test_backend.py` が大量のテストを持つのは、こうして1つずつ「守るべき仕様」を積み上げてきた結果です。

## 18. この章のまとめ

- **テストは「機械にやらせる動作確認」**。健康診断のように、コードを直すたびに流して「壊していないか」を一瞬で確かめる、保守の最後の砦。
- どんなテストも **3ステップ**（準備 Arrange → 実行 Act → 検証 Assert）。検証＝**アサーション**（「〜のはず」を主張し、違えば失敗）。
- **フロント** は **Vitest ＋ React Testing Library**。`Login.test.tsx` 全132行を1行ずつ読み、`vi.mock`（画像・API・navigate のモック化）、`describe`/`it`/`beforeEach`、`render`/`screen`/`fireEvent`/`waitFor`、`getByRole`/`getByLabelText`/`findByRole`、`mockResolvedValueOnce`/`mockRejectedValueOnce`、そして **成功遷移・エラー表示・401遷移・別エラー** の各テストを完全に理解した。
- 要素取得は **`getBy`（最初からある）/ `findBy`（後から出る・待つ）/ `queryBy`（無いことの確認）** を使い分ける。
- **バック** は **Django `TestCase` ＋ `APIClient`**。`test_backend.py` の土台（`make_break_times`・`BaseTestCase`・`login` ヘルパー）と `TestModels` を1行ずつ読み、`assertEqual`/`assertIn`/`assertTrue`/`assertFalse`/`assertLessEqual` を理解した。
- APIテストの王道は **「未ログイン→401 / 正しい権限→200 / 権限不足→403」の3点セット**。401（誰か不明）と403（権限不足）の違いが肝。作成は201・削除は204も確認する。
- テストは **専用設定**（`test_settings.py`：使い捨てSQLite・即時実行・マイグレーション省略）で動かす。実行は **`npm run test:run`** と **`python manage.py test --settings=hozen_another.test_settings`**。`✓`/`OK` が出れば全合格。
- 失敗したら **メッセージ（期待と実際の差）を読み**、本体を直すかテストを更新するかを判断する。理解せずに消さない。
- **新テストは似た既存テストをコピーして一部を変える**。バグを直したら再発防止のテストを1つ足す。
